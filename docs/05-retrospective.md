# 实现复盘

以下是本项目实际实现与验证过程的工程复盘。候选人个人亲历与收获仍应按[参与记录](17-candidate-participation.md)据实登记。

## 最难的问题：成功事实和执行意图不能混为一谈

生成成功后保存失败，已经发生的模拟费用不能清零；续跑也不能再收费。模型说“完成”不等于保存成功。实现以工具结果、依赖守卫、费用账本和保存事务为准，保留失败步骤与可复用成果。

恢复还要区分已落盘决定、本地未提交结果和外部未知结果。已确认决定可重放，本地无远端副作用工具可按事务语义重做，外部请求可能已执行时则必须保留意图并阻断重发。没有查询或幂等契约，不能把“未知”推断成“没发生”。

## 实际发现和改进

| 问题 | 观察与处理 |
| --- | --- |
| 状态与租约分开读取 | 并发中曾误报刚完成任务需恢复；改为同一SQLite快照观察，保留失败和20轮复测 |
| 取消检查与动作登记分离 | 曾在取消后产生8个模拟单位；把裁决放入同一写事务，测试确认不启动新生成 |
| 已有库重复申请迁移写锁 | 短负载出现锁等待；已初始化schema只读核验，不反复写迁移 |
| 忙锁异常和拒绝请求竞争 | 忙锁改为STATE_BUSY；容量满先只读拒绝，写事务内再次校验，减少占用已接纳任务写槽 |
| 提供商503时批次继续请求 | 增加明确停止和not_run_cases，保留Retry-After，不把未运行条目算通过 |
| 测试器续跑未重新等待容量 | 这是测试器问题；修正有界等待和5秒尾部排空，保留原不通过数据 |
| 过短人工租约影响恢复/容量测试 | 仅对被杀拥有者加速到400毫秒，恢复/容量控制使用实际60秒，不降低状态和费用断言 |

无节流饱和运行的4817场景中有1次明确保存失败，费用与未保存事实没有虚报。该记录保留；后续约4个新任务/秒的固定负载、独立16进程突发、故障矩阵分别统计，不混用分母或声称任意压力下都成功。

## 工程收获

1. 将业务要求变成可失败的不变量，再让AI实现，比只要求“写一个Agent”更容易检验质量。费用、依赖和保存回执都可以在公开接口核对。
2. 一次测试失败可能是产品缺陷、提供商问题或测试夹具假设错误。应先缩小复现，再修原因，不能为通过而降低要求，也不能把所有red都包装成业务发现。
3. 原生有限循环足够完成本题；框架不能替代业务幂等、费用与失败语义。新增保障也增加复杂度，应保持接口稳定，避免额外插件和服务层。
4. 短期验证应声明到达率、并发、数据和模型边界。零跳过、保留失败和版本一致能提高可信度，但不等于代码全覆盖或长期SLA。
5. AI适合批量实现、构建故障复现和整理证据；需求取舍、事实核对及对结果负责仍需要清楚的人类判断与参与记录。
