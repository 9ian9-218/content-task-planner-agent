# 短期验收与最终交付计划

本计划按用户最新约束修订：本项目是题目2的校招 CLI 工程，不要求长期在线、共享服务或真实生产业务接入。此前的24小时/1万任务、7天试点和50组独立留出目标归入未来生产化路线，不作为本次提交的必过条件。短测通过也不宣称证明长期SLA。

## 本次必须完成

| 层次 | 验证与材料 | 通过条件 |
| --- | --- | --- |
| 题面核心 | 正常、缺预算/截止时间、工具失败、预算超限、重复执行 | 当前代码的实际输入/输出/Trace可逐项对应；费用、依赖和保存事实一致 |
| 动态决策 | 真实模型正常与报价变化路径；重规划重复观察 | 读取到超预算12后，模型改询价8并保存；失败不能写为成功，不交内部思维过程 |
| 工程回归 | 全部公开Planner/CLI/外部HTTP边界测试 | 全通过、关键平台测试零跳过、前后代码指纹一致 |
| 短期稳定性 | 5分钟、8客户端、每客户端每2秒一个新需求（约4个/秒）、同库最多2活跃任务的混合负载 | 至少300个已核验场景，硬约束/回执错误0；报告拒绝率、耗时、线程/FD/RSS，检查结束无线程/连接泄漏 |
| 并发与恢复 | 16进程×20轮同请求；8故障位置×10轮 | 无重复方案和模拟费用；旧代次写回被拒；未知外部结果阻断 |
| 模型评估 | 当前代码完整18点真实矩阵、2个对抗场景、3轮重规划 | 明确预期/实际和失败；每批设请求上限，不把失败或缺usage当0账单 |
| 可复制交付 | 清洁目录运行、离线入口、依赖/.env.example、无密钥 | 只用交付包和公开步骤可运行、查看输入输出与全部证据 |
| 提交说明 | 题号、GitHub URL、最终SHA、AI使用/个人贡献/用时、未完成项 | 不编造未知个人工时和贡献；本地包完成后补入真实远程信息 |

## 实施顺序

1. 沿用已确认的Planner公开接口、CLI/评估命令和外部模型/OS边界，继续使用Matt Pocock TDD，先完成短测器的实际red/green。
2. 冻结业务源码，先启动离线短负载，并行进行有请求额度的当前版本真实验收；有新业务修复才重跑相关回归和必要模型场景。
3. 建立逐条题面验收矩阵、评审入口、实际结果摘要和完整必交文档。历史材料保留为阶段记录，当前入口不引用旧指纹冒充当前结果。
4. 从白名单生成干净交付目录，检查密钥/私有配置、文档链接、JSON和证据指纹；在交付目录运行CLI和回归检查。
5. 生成提交说明和可上传压缩包；远程仓库由用户提供后再提交并核对真实SHA。题面未规定仓库名称，示例仓库名不是必选命名。

## 明确边界

业务资料、成本和耗时允许合成Mock；真实模型决策证据单独标记。5分钟负载采用离线模型以避免网关压测，仅验证执行器、状态与资源行为。生产身份授权、远端扣费对账、长期SLA和真实运营收益不属于本题承诺。

CI定义与本地等价命令分开报告；未在GitHub执行就不写云端CI通过。已记录候选人确认的约一天半实际用时，个人具体手工修改与独立复现仍按事实登记，自动化日志跨度只作为AI执行记录。

短期负载采用已声明到达率，瞬时冲击由16进程竞争矩阵覆盖。此前无节流饱和运行的4817场景/1次明确保存失败完整保留；它不被删除或称为零失败。固定负载测试与饱和上限探索分别报告，不能混用分母。
