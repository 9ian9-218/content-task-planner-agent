# 项目实现计划

> 本文保留最初核心实现预算与阶段安排。当前用户要求的短期交付以[15号计划](15-short-validation-and-delivery.md)为准；一天半参与计划见[17号文档](17-candidate-participation.md)，它不等于实际个人工时。

版本：v0.3；日期：2026-10-28；状态：原 MVP 核心实现、离线验证、真实模型验证和续跑已完成。以下阶段时间仍是原计划分配，不能当成实际工时。题号 2，范围以 [PRD](01-requirements.md) 为准，实际结果见 [03-evaluation.md](03-evaluation.md)。工业补全另按[单机 CLI／多进程稳定性计划](12-stability-hardening-plan.md)执行。

## 1. 实施策略

先尽快验证真实模型能完成一次工具调用闭环，再实现预算/时间核验与状态保存，随后把模型接入同一套工具。开发过程中同步保存输出，最后运行真实对照路径并整理材料。

不以画布、截图或预设日志替代实现。不把“已成功串行执行四个工具”直接当成动态重规划达标。不让可选界面、框架学习或额外模型接入挤占必须验收。

下面的 180 分钟是**进入开发后的估算分配**，不是实际完成承诺，也不是考核实际用时。最终时间记录应包含已经发生的需求分析、调研、开发、调试和材料整理，不能只统计编码阶段。当前规划阶段没有可靠的逐分钟工时记录，不补造用时。

## 2. 三小时核心计划

| 阶段 | 时间预算 | 具体任务 | 交付与完成门槛 |
| --- | ---: | --- | --- |
| M0 可用性验证 | 0–15 分钟 | 检查 Python 环境；读取环境配置；以默认候选模型完成真实“选工具→本地执行→回传→下一次响应”冒烟；记录接口、模型名与参数 | 真实调用确实成功，或明确记录不可用原因并保留阻塞项；不能用 Mock 替代冒烟结果 |
| M1 数据与执行基础 | 15–50 分钟 | 建立少量合成素材、两档费用/耗时、正常/报价变化/保存失败场景；实现输入校验、SQLite 三张表、账本与时间核算；实现四类工具 | 不接模型也能核对 12/8 报价、失败状态、保存唯一性与等值边界 |
| M2 Agent 核心链路 | 50–95 分钟 | 实现 live/mock Adapter、消息历史、工具分派、硬约束、上下文结果保留、执行上限和 Trace；增加 CLI 与结构化输出 | Mock 能跑正常、超预算重规划和保存失败；工具错误确实进入下一次决策输入 |
| M3 验收回归 | 95–135 分钟 | 按矩阵覆盖 P0；核对缺预算/截止时间、重复执行、费用/时间上限、非法动作、模型不可用；导出离线实际材料 | 全部 P0 确定性测试通过，记录实际结果；失败点修复后仅重跑相关用例及核心回归 |
| M4 真实决策与改进 | 135–165 分钟 | 运行 C01/C04 两条不同真实路径；尽量补 C03；检查 Trace 与最终状态；若失败，修改工具描述或提示词后重测并保留修改依据 | 有至少两条真实路径；无法达成时明确为未完成，保存实际失败记录，不人工补写成功日志 |
| M5 交付核验 | 165–180 分钟 | README 安装/运行入口；更新评估、AI 使用与复盘；清理凭据；核对文件引用及题号 | 新环境命令可用；所有实际结果可追溯；最终 URL 与 SHA 在用户授权的提交阶段填写 |

M0 没有凭据或网络时继续 M1–M3 和文档工作，live 证据保持待完成；不能宣布完整满足模型决策要求。30 分钟时若还在排查接口，暂停扩展性适配，固定一个可用服务商或如实记录阻塞。

## 4. 真实模型接入的开工检查

以下是开发任务，不是当前已经执行的检查：

1. 用户通过本地环境提供可用凭据，项目只读环境变量，仓库保存 `.env.example`。
2. 使用用户指定的 `http://100.73.185.103:8045/v1` 与 `claude-opus-4-6-thinking`（网关实际公开 ID）；原生工具调用和实际核心路径已验证，完整结果及限制以当前评估报告为准。
3. 确认工具参数、工具响应关联 ID、非流式响应、错误码和超时行为；普通模式仍做本地参数校验。
4. 记录真实模型和运行配置，固定合成数据、提示词版本及测试业务起点。
5. 模型不可用不影响离线流程开发，但在 README 和评估中保留“真实决策未验证”的明确说明。

## 5. 必须先通过的验收门槛

| 门槛 | 判定 |
| --- | --- |
| G1 核算正确 | 估算 12 超预算 10；替代 8 可行；等值预算和等值截止允许；失败耗时不清零 |
| G2 状态可信 | 生成成功、保存失败时只能未完成；已有脚本可检查；保存记录不存在时不能返回成功 |
| G3 防重复 | 同请求两次只保留 1 份方案，收费步骤只成功执行 1 次；同 ID 不同输入明确冲突 |
| G4 动态选择 | 真实模型看到不同报价/工具结果后选择不同后续动作，有实际 Trace 支持 |
| G5 有界执行 | 预算、时间或步骤限制被触发后不越界继续，返回明确原因和部分结果 |
| G6 可复现与诚实 | 命令、数据、实际输出、测试和文档相符；Mock、真实模型、待做内容均能区分 |

若 G1–G3 未通过，优先修复核算与保存；不先追求生成文案质量。G4 尚未完成时可以交付离线原型，但不能把整体状态标为考核完整达标。

## 6. P1 加分计划与停止条件

只有所有 P0 确定性用例通过，且真实模型已经有两条不同路径后，才考虑下面的工作。额外用时应计入真实工时。

| 扩展 | 预计增量 | 范围与验证 |
| --- | ---: | --- |
| 失败步骤续跑 | 30–45 分钟 | 仅在相同需求、资料和费用版本下支持 `--resume`；恢复账本，复用脚本，从失败保存开始；C14 验证脚本不重做 |
| 模型稳定性观察 | 15–30 分钟及实际调用等待 | C01/C04 各运行 3 次，报告实际通过次数、失败原因，不作泛化承诺 |
| 一次针对性改进 | 20–30 分钟 | 针对实际发现的问题修改提示词、工具说明或返回字段；对同一场景比较改前/改后结果并保留记录 |

P1 不演变为通用工作流引擎。若续跑涉及真实远端副作用、未知扣费或多进程恢复，应记录为后续工作，本期不承诺生产级可靠性。

## 7. 最终提交检查

- 题号为 2；README 能定位需求、技术方案、实际评估与运行入口。
- `src/`、`tests/`、`data/`、`examples/`、依赖清单与 `.env.example` 在实际实现后齐全。

- 至少两条真实模型决策路径；Mock 入口及边界明确。
- 测试日志含真实命令、结果与时间；评估文档链接存在的结果文件。
- 实际用时、AI 参与、候选人亲自修改与验证据实记录，未完成功能明确列出。
- 不含真实密钥、私人资料或内部思维过程；来源与所用框架/依赖版本按实际使用填写。
- 实际提交时填写 GitHub URL、最终 commit SHA，并确保评审可访问；当前文档阶段不伪造这些信息。
