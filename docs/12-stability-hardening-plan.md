## 1. 目标和当前基线

本阶段交付一个在单台主机上可以安全竞争任务、处理异常中断、保留执行事实、限制开销并能定位失败的 CLI Agent。继续只保存方案，不执行内容发布。共享 HTTP、多租户和跨主机执行放到后续独立阶段。

现有基线：63/63 自动化测试、18/18 完整真实场景、2/2 对抗输入；最后一轮真实请求 79 次。它们支持当前 MVP 的行为，不证明下列稳定性功能已经存在。源码指纹及逐文件清单保存在 [baseline.json](../examples/hardening/baseline.json)，完整任务依赖与验收门槛保存在 [stability-backlog.json](stability-backlog.json)。

质量保障分为三类：程序必须维持的硬性不变量、通过实验衡量的模型效果、需要真实环境证明的运行能力。任何一类未过门槛，都不能仅凭测试总数或自评分上升宣称生产就绪。

## 2. 新核验的运行时前置条件

当前实际环境是 Python 3.10.12、SQLite 3.37.2。Python 官方版本表列明 3.10 已于 2026-10-01 结束支持，生产目标采用仍受支持的 Python 3.14 补丁发行版，实施时固定实际补丁号和来源。[Python 官方版本状态](https://devguide.python.org/versions/)

当前实现没有主动启用 WAL；新建临时文件库实测 journal_mode=delete。未来若为并发选择 WAL，必须先核验 SQLite 修复或发行版回移证明，并确认同一主机、本地文件系统。官方文档记录 WAL-reset 在并发写入/检查点条件下的问题及修复版本；不能只看旧版本字符串就判断发行版是否带有回移补丁，也不能为性能直接开启未经验证的 WAL。[SQLite WAL 官方说明](https://sqlite.org/wal.html)

默认先保留回滚日志，通过实际容量测试决定是否需要 WAL。Windows/WSL 挂载盘、网络共享盘和 Linux 本地文件系统分别记录环境；未验证的平台不列为生产支持。备份采用数据库一致性接口，具体实现与当前目标 Python 版本一致。[Python 3.14 sqlite3.backup](https://docs.python.org/3.14/library/sqlite3.html#sqlite3.Connection.backup)

本阶段的任务身份、并发及累计额度以同一状态库为范围，部署配置采用一个明确的状态库。使用独立 --db 文件代表独立执行域，不能宣称它们共享全主机配额或跨库防重复；真实远端工具还需自己的全局幂等/对账契约。

## 3. 必须始终成立的规则

1. 同一需求的方案最多保存一份；同一已确认成功的付费业务操作复用结果，不再次计业务费用。
2. 已发生费用、成功脚本、保存回执不能因重试、取消、超时或恢复而清零或丢失。
3. 模型无法增加用户硬预算、延后截止或绕过依赖；只有明确保存事务才能产生 completed。
4. 续跑不重置任务累计限额，不允许通过修改 CLI 参数提高原任务授权上限。
5. 旧所有者失去执行资格后，不能启动新动作或覆盖新所有者结果。
6. 外部动作可能成功但尚无回执时，明确标为结果不确定；先查询或对账，不自动按失败重做，也不宣称免费。
7. 取消与保存提交竞争时以提交事实为准。已经保存的方案保留回执并报告取消到达过晚；未开始的新动作不得继续派发。
8. 导出失败不改变数据库保存事实；旧目录中的产物不能被误当作本轮成功产物。
9. 公开日志不包含密钥、内部思维字段或测试用敏感哨兵；真实资料的保存与导出遵守明确访问和留存策略。
10. 质量门槛的 skipped、not_run、outcome_unknown 和 failed 分开记录，不能并入通过。

## 4. 核心设计

### 执行所有权和恢复

任务记录持有 owner_token、generation、lease_expires_at、heartbeat_at。领取和接管在一个事务中完成，generation 单调增加。写回、派发动作、保存和终结都验证当前所有权；心跳使用独立数据库连接，避免与主线程错误共享连接。

拟定租约 60 秒、心跳 10 秒，后续由慢响应、暂停进程、数据库锁和时钟变化测试校验。到期仅表示可以进入恢复检查，不能证明旧请求没有远端副作用。status/recover 在一次调用内识别过期状态；CLI 尚未部署监督进程时不承诺后台自动发现时间。

操作记录包含稳定逻辑键、执行意图、尝试编号、所有者代次和回执。先提交意图，再执行，再提交结果。已确认结果复用；进程在外部结果确认前中断时进入 blocked/reconcile_required。真实工具缺少幂等键或结果查询能力时保持阻断，不能凭本地锁保证远端 exactly-once。

当前公开业务状态继续区分 completed、incomplete、needs_input、invalid_request。租约、等待对账和取消等作为额外运行状态及原因码，不把 running 或结果不确定包装成业务成功。

### 开销和重试

任务创建时固化限额与策略版本；拟定模型请求和业务工具尝试各最多 12 次，续跑共享余额。网络重试、格式错误和结果不确定的尝试都计入模型请求额度；原生 finish_task 仍计入模型决策额度。

永久错误、瞬态错误、结果不确定分别处理。永久错误不能原样重试；瞬态错误按剩余时间、Retry-After 和最多两次重试决定是否仍可派发；结果不确定先查询。模型仍可根据真实观察决定换方案或停止，程序负责限制危险或超额动作。

模拟业务单位、模型 Token 和货币金额分账。请求次数可以设置硬上限；已报告 Token 阈值只能停止后续派发，最后一次请求可能越过阈值。价格、计量和最大输入边界未核验时不宣称硬性货币预算成立。未知账单先保留额度，不能当作零费用返还。

180 秒仍是停止派发语义。若新增外部等待总时限，采用可终止的调用隔离并记录被中止调用的未知结果；不能将 socket 空闲超时当作总时长保证。已进入本地提交的事务按实际结果处理，不假称任意时刻都能抢占回滚。

### 存储、导出和隐私

存储记录 schema/context/policy 版本，迁移失败回滚；遇到不认识的新版本拒绝写入。旧 running 没有所有者和执行意图时保持显式待处理，不能自动断言已崩溃。备份使用一致快照，先恢复到新文件并核验，再切换；保留原库。

每次运行产物写入独立 run_id 目录。临时产物完成并校验后发布索引；消费者只读取已发布清单。保留现有输入/配置/数据库路径保护。提纲换行在明确的文本表示层处理，原始模型参数与实际 JSON 保留来源，不重写历史 Trace。

运行日志保留任务 ID、操作键、版本、状态、耗时、重试和用量；敏感正文与一般运维日志分开。生产配置验证文件权限、网络目标和传输保护。用户此前授权的开发网关继续可用于开发验证；共享/生产用途的传输安全需要实际证明。

8 个故障位置包括：领取前后、模型派发后未取得回执、模型结果已持久化但工具未执行、工具意图已写未执行、工具已执行但回执未写、保存已提交但汇总未写、产物写入中。最后两项分别验证保存事实和产物发布，不要求每种故障都能自动成功结束。

## 7. 模型评估的独立性与开销

开发回归集可用于修复；留出需求及标签应由独立验收人封存，调参不能接触留出答案。若目前只有 AI 自评，就保持独立评估门槛待完成，不虚称盲测。模型效果、执行器正确性和外部网关可用性分别报告。

同一需求重复三轮用于衡量重复稳定性，不将三轮当作三个独立需求。报告各类分母、真实调用数、观察后动作变化、无依据事实、未知结果和技术失败；若提供置信区间，按需求组和采样方式计算。不能因点估计达到目标就宣称总体可靠性已被证明。

既有网关访问授权保留；扩展批次先配置具体请求上限、Token 派发阈值及停止条件。当前规划阶段新增模型请求为 0，不执行未设边界的大批付费评估。真实货币计价、计量或结果查询缺失时，相关门槛保持待验证，开发和确定性故障测试仍可推进。

## 8. Matt Pocock TDD 执行约束

继续使用已确认的公开测试位置：Planner.run/resume、保存结果公开查询、CLI 及导出、LiveModel 外部 HTTP、公开评估命令。未来 status/recover/cancel/backup/restore/doctor 通过真实用户入口验证；不直接查询私有表来代替业务断言。

每次只做一个行为：写出独立预期 → 实际 red → 最小实现 → green → 必要的相关回归。先实现单个故障点，再扩展故障位置；不先堆齐全部测试再补实现。仅替换外部 HTTP、工具、时钟等可控 seam；迁移、进程终止、锁冲突和文件故障尽量使用真实数据库/子进程/文件系统。

不为行覆盖率或测试总数而增加同义测试。每个工作包完成必须有代码、真实运行证据、相关回归及已知限制更新。当前工业评分不因计划已写而自动上调。

## 9. 版本和证据管理

新增验证使用独立的 examples/hardening/<阶段>/ 目录，记录源码、策略、schema、素材、模型和环境版本；旧例保持原指纹。每个发布候选重新运行相关确定性回归及预算内的模型对照路径，保存失败，不挑选成功样本。

当前 .git/HEAD 不存在，基线文件清单不等于已经创建 Git 提交或标签。GitHub 发布与最终 SHA 仍需实际完成。进度以 backlog 中的状态和证据链接更新，只有写计划不能将 planned 改为 completed。

首个实现顺序：STAB-00 的受支持运行时及版本诊断 → STAB-01 的迁移/备份 → STAB-02 的单次领取与旧代次隔离 → STAB-03 的首个中断恢复行为。之后再扩展累计额度、取消、重试和完整故障矩阵。
